# 구현 - 작업 분리와 변경 확인

## 1. 담당 선택

작은 편집과 사용자와 막 합의한 미묘한 동작은 메인이 처리한다. 독립 모듈, 큰 조사/편집량은 위임해 메인 컨텍스트를 줄인다. 이득은 분리할 작업량과 명세 작성/검수 비용으로 판단한다.

생산 서브는 편집 가능한 general-purpose를 사용한다. 모델과 effort는 [model-routing.md](../notebook/common/model-routing.md)의 운영 표를 따른다.

## 2. 위임 명세

명세 파일에는 다음 재료만 넣는다.

- 목표와 이 묶음의 변경 방식(플랜의 해당 절)
- 수정할 파일, 가까운 레퍼런스 경로와 필요한 위치
- 공유 타입/API/문자열 계약, 관련 지침, 걸리는 노트북 lessons 경로("먼저 읽고 대조하라" - 히트 0 이면 `없음`이라고 명시한다), nb-grep 호출법(서브가 만나는 새 이름은 스스로 대조한다)
- 검증 명령과 확인 범위, 수용된 리스크 - 컴파일/문법 확인 수단은 플랜이나 노트북에 확인 명령이 있으면 그대로 싣고, 없으면 "확인 불가로 보고하라"를 싣는다(수단 없이 "확인했다"는 보고를 받는 구조를 만들지 않는다)
- `$WORK` 절대경로, 반환할 결과

공유 계약을 만드는 작업을 먼저 실행한 뒤 소비 작업을 병렬화한다. 같은 파일은 한 담당자가 맡는다. 시작 시점에 다른 작업자의 변경을 기록하고 그 변경을 보존한다.

### 서브 계약

명세에 없는 파일, 심볼, 외부 서비스, 에러 문자열을 만나면 `nb-grep.sh "$WORK" <이름>`으로 대조한 뒤 진행한다. 합의된 범위와 계약에 맞춰 구현한다. 단순한 줄번호/위치 차이는 라이브 근거로 보정한다. 사용자 의도, 공개 계약, 데이터 해석 또는 작업 범위를 바꿔야 하는 불일치는 멈추고 근거와 이미 변경한 파일 목록을 반환한다. 변경분은 메인이 판단할 수 있도록 남긴다.

반환은 변경 파일별 요지, 실행한 검증과 결과, 미검증/질문, 재사용할 스크립트 경로다. 메인은 실제 diff를 볼 수 있으므로 파일 본문과 diff 전문은 반환에 넣을 필요가 없다.

## 3. 구현과 검수

1. 가장 가까운 기존 구현을 본떠 차이 나는 부분만 바꾼다(복제 후 적응). 레퍼런스가 컨벤션을 어기고 있을 수 있으므로 구조만 가져오고 스타일은 컨벤션 기준으로 맞춘다. 기존 진입점 밖의 우회로, 중복 시스템, 새 헬퍼는 만들지 않는다. 새 동작의 인자와 부수효과는 호출자 값을 그대로 넘기지 말고 현재 요구에서 도출한다.
2. 변경된 코드에 프로젝트 컨벤션을 적용한다. 포매터/린트가 확인한 규칙은 그 결과를 사용하고, 도구가 확인하지 않는 관련 규칙만 직접 점검한다.
3. 새로 추가/변경한 문자열 키, 리소스 경로, 직렬화 참조는 실제 대상과 연결되는지 확인한다. 이미 확인했고 바뀌지 않은 값은 근거를 재사용한다.
4. 메인은 세션 변경 목록과 diff 규모를 확인한다. 위임분에서는 공유 계약, 진입점, 위험한 데이터 연결을 표본 확인하고 나머지는 P4의 실행 검증으로 확인한다.
5. 생산 직후 위치의 단계 카드가 적용되면 안전 조건을 확인하고 실행한다.

## 4. 스크립트 재사용

반복 변환/집계/설정 작업(일괄 이동, 치환, 집계, 설정 변경)은 노트북의 scripts INDEX를 projects → stacks → common 순으로 먼저 확인한다. 이미 있으면 그 스크립트를 쓴다 - INDEX의 "어떻게" 항목이 호출법이다. 새 스크립트는 `$WORK`에 보관한다. 반복 사용이 예상되는 도구만 P5에서 경로와 사용 목적을 curator에게 제안한다. 특정 파일 한 번만 고치는 명령은 보관할 기록이 아니다.
