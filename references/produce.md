# 생산 - 복제 후 적응, 위임 생산, 컨벤션 점검, 스크립트 보존

> 기본 방식은 "처음부터 작성"이 아니라 "인터뷰에서 확정한 레퍼런스를 복제한 뒤 차이 나는 부분만 수정"이다.
> 검증된 패턴을 따르므로 빠르고 환각이 줄어든다. P2 를 통과한 플랜의 설계가 유일한 스펙이다. 생산 중에 설계를 즉흥적으로 바꾸지 않는다 - 바꿀 이유가 생겼다면 P1/P2 로 되돌아간다.

## 1. 위임 판단 - 누가 쓰는가부터 정한다

생산을 시작하기 전에 변경 설계를 묶음으로 가르고, 묶음마다 "메인 직접 / 서브 위임"을 판정한다.

- **위임한다:** 파일 3개 이상을 만들거나 고치는 묶음, 또는 다른 묶음과 파일이 겹치지 않는 독립 모듈. 대량의 Edit/Read 가 메인 컨텍스트에 쌓이지 않는 것이 이 스킬 최대의 비용 절감 지점이다. 생산 서브는 `agentType` 을 생략해(general-purpose) 스폰한다 - 편집 도구가 필요하므로 Explore 는 쓸 수 없다. 모델과 effort 는 [../notebook/common/model-routing.md](../notebook/common/model-routing.md) §3 의 고정 배치를 따른다(위임 생산 = 상위 티어 명시, effort 는 생략해 세션 상속, 세션 `max` 면 `xhigh` 명시). Workflow 로 여러 묶음을 병렬 생산할 때도 `agent()` 옵션에 `effort` 키를 넣지 않는다.
- **메인이 직접 한다:** 1~2파일 수정, 방금 사용자와 합의한 미묘한 디테일이 관련된 수정, 다른 묶음과 강하게 얽혀 순서 조율이 계속 필요한 수정. 이런 것까지 위임하면 작업 명세 작성과 검수 왕복이 편집 자체보다 비싸진다.

### 작업 명세 규격 (위임 프롬프트에 들어가는 전부)

서브는 메인의 대화를 모른다. 작업 명세만이 서브의 세계다:

1. 이 묶음의 **변경 설계 절**(플랜에서 발췌 - 파일별 무엇을/방식) + **코드 초안**
2. **대상 파일 경로 목록**과 **레퍼런스 file:line** (본문은 붙이지 않는다 - 서브가 라이브로 읽는 쪽이 싸고 최신이다)
3. 이 묶음에 걸리는 **컨벤션 규칙 목록** (컨벤션 점검의 기준이 된다)
4. 걸리는 **노트북 lessons 경로** ("먼저 읽고 대조하라")
5. **알려진 수용 리스크** (P2 에서 사용자가 수용한 것 - 재론 금지)
6. `$WORK` 절대 경로 (임시 스크립트를 여기 보존 - 변수 표기가 아니라 리터럴 경로로)
7. **컴파일/문법 확인 수단** - 플랜이나 노트북에 확인 명령이 있으면 그대로 싣고, 없으면 "확인 불가로 보고하라"를 싣는다. 수단 없이 "확인했다"는 보고를 받는 구조를 만들지 않는다
8. 아래 **'서브 계약' 소절** 전문

**완결성 확인:** 작업 명세를 닫기 전에 스스로 묻는다 - "이 작업 명세만 읽고 남이 구현할 수 있나?" 대화에서 한 얘기를 풀어 설명하고 싶어지면, 그 내용을 플랜에 먼저 옮기고 작업 명세는 플랜을 발췌한다. 플랜에 없는 컨텍스트는 서브에게 존재하지 않는다.

### 모듈 경계 계약 (여러 묶음으로 쪼갤 때)

- 묶음들이 **공유하는 심볼**(타입, 시그니처, 문자열 키, enum 멤버)은 관련된 모든 작업 명세에 똑같이 명시한다. 한쪽에만 있으면 다른 쪽이 임의로 지어내 정의가 갈라진다.
- 공유 심볼을 **새로 만드는** 묶음을 먼저 순차로 실행하고, 그것을 소비하는 묶음들을 그 뒤에 병렬로 실행한다.
- **같은 파일을 만지는 묶음은 병렬 금지다.** 순차로 돌리거나 한 서브로 합친다.

### 서브 계약 (작업 명세에 그대로 싣는다)

- 플랜의 설계가 유일한 스펙이다. 설계 변경 금지 - 바꾸고 싶은 이유가 생기면 그것이 곧 불일치다.
- **불일치 보고:** 플랜의 전제와 실물이 다르면(시그니처 불일치, 파일 부재, 레퍼런스가 플랜 서술과 다름) 임의로 우회하지 말고 작업을 멈추고 '불일치 보고'만 반환하라 - 무엇이, 어디서(file:line), 플랜의 어느 전제와 다른지, 그리고 **중단 시점까지 이미 변경한 파일 목록**. 변경분은 되돌리지 말고 그대로 두라 - 처리는 메인이 git 으로 보고 정한다.
- 컨벤션 규칙 목록과 항목별로 대조해 위반 0 을 확인하라.
- 반환 규격: 변경 파일 목록 + 파일별 요지 1~2줄 + 컨벤션 점검 결과 + 컴파일/문법 확인 결과(수단이 없었으면 '확인 불가') + `$WORK` 에 만든 임시 스크립트 경로 목록 + 남은 질문. **diff 전문과 파일 본문은 반환하지 마라** - 메인은 git 으로 직접 본다.

### 메인 검수 (반환을 받으면)

- `git diff --stat` 으로 규모가 플랜과 맞는지 대조한다.
- 위험 지점만 라이브로 표본 확인한다: 문자열 키/id 실재, 진입점 연결부, 모듈 경계 계약 지점. 전량 재독은 위임의 이득을 상쇄한다.
- 불일치 보고가 오면 해당 지점만 P1 재진입한다(치명 지적과 같은 경로).

## 2. 복제 후 적응 절차

1. 레퍼런스 파일을 연다(플랜에 file:line 으로 확정되어 있다). 구조, 진입 경로, 명명을 그대로 따른다.
2. 차이 나는 부분만 바꾼다. 플랜의 변경 계획에 없는 것은 건드리지 않는다.
3. 새 우회로를 만들지 않는다. 기존 진입점을 우회하는 새 메서드, 매니저, 중복 시스템은 금지이며, 필요하면 기존 진입점을 확장한다.

## 3. 복제 후 적응의 3대 함정 (컴파일은 통과하는데 의미가 틀어지는 종류)

1. **컴파일러가 보증하지 못하는 값에 동작을 걸 때는 실재부터 확인한다.** 문자열 키, id, 경로, 상태명에 분기나 조회를 걸 때는 그 값이 코드나 데이터에 실제로 존재하는지 쓰기 전에 확인한다. 존재하지 않는 값에 걸면 영영 발동하지 않는 데드코드가 되는데, 컴파일은 통과하므로 잡히지 않는다. P2 의 렌즈 ⑤가 초안 수준에서 봤더라도, 생산 중에 새로 등장한 값은 그때그때 다시 확인한다.
2. **진입점을 재사용할 때 인자는 스펙에서 다시 도출한다.** 기존 진입점을 다시 호출해 부수효과를 얻는 것은 옳지만, 넘기는 각 인자를 호출자가 받은 값 그대로 전달해서는 안 된다. 호출자의 인자는 호출자의 맥락에 맞춰진 값이라 새 동작에는 맞지 않을 수 있다.
3. **새로 추가하는 멤버는 대상 파일이 구식이어도 컨벤션을 100% 지킨다.** 기존 줄을 건드리지 않는 것과 새 줄을 구식으로 쓰는 것은 다른 문제다. 새로 추가하는 코드는 컨벤션 문서를 그대로 적용한다.

## 4. 컨벤션 점검 (생산 직후, 생략 불가)

"이번 작업에 걸리는 컨벤션 규칙 목록"을 방금 쓴 코드와 항목별로 대조한다. "쓰면서 조심했다"로 대체할 수 없다. 사전 리뷰(P2)는 컨벤션을 보지 않았으므로 이 점검이 컨벤션의 유일한 관문이다. 위반은 즉시 수정하고, 문서에 없는 규칙을 만들어서 잡지는 않는다.

- 메인 직접 생산분: 메인이 수행한다.
- 위임 생산분: 서브가 작업 명세의 규칙 목록으로 수행하고 "위반 0"을 보고한다. 메인은 표본만 재확인한다.
- 벌크(다파일 반복) 생산이었다면 `model: 'haiku'` 서브에 "스타일 문법만 제자리 교정하라"고 위임할 수 있다. 단 구조와 진입점 변경 금지 조건을 명시하고, 반환은 수정 파일 목록 + 교정 건수만 받는다(diff 전문 금지 - 메인이 `git diff` 로 직접 확인한다).

## 5. 스크립트 보존과 재사용 (매 작업)

- **작업 전:** 반복성 작업(일괄 이동, 치환, 집계, 설정 변경)을 만나면 노트북의 scripts INDEX 3레이어을 projects → stacks → common 순으로 먼저 확인한다. 이미 있으면 그 스크립트를 쓴다. INDEX 의 "어떻게" 항목이 호출법이다.
- **작업 중:** 임시 스크립트는 지우지 말고 `$WORK` 아래에 만들어 둔다(위임 서브에도 같은 규칙을 작업 명세로 전달한다).
- **작업 후(P5):** 메인은 재사용 가치가 있는 스크립트의 **등록 제안**(경로 + 재사용 근거)만 만들어 curator 에게 넘긴다. 레이어 판정, `scripts/` 로 옮기기, INDEX 등록은 curator 가 한다(노트북 쓰기는 curator 단일 주체 - SKILL.md 준칙). 등록 문구 규격은 [agents/curator.md](../agents/curator.md) §2 에 있다 - 왜 / 언제 / 어떻게 / 결과의 확정 톤이고 "~할 때 쓰면 좋다" 같은 권장 톤은 금지다.
- 1회성이 명백한 것(특정 파일 하나를 고치는 sed 한 줄)은 등록하지 않는다. INDEX 가 커지는 것도 비용이다.
