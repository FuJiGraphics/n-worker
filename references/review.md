# 사전 적대 리뷰 - 난이도 판정, 렌즈 정의와 카탈로그, 교차 검증, Workflow 골격

> P2 에서 "쓸 코드"(파일별 변경 계획 + 핵심 코드 초안)를 생산 전에 허점을 찾는 단계의 상세다.
> 모든 리뷰 서브에게 주는 공통 명령은 하나다: **"통과시키지 말고 허점을 찾아라. 칭찬과 범위 밖 이야기는 금지. 모든 지적은 path:line 인용."**
> 모델과 effort 값의 단일 기준은 [notebook/common/model-routing.md](../notebook/common/model-routing.md) 와 이 파일의 표다. 교차 검증(세트 복제) 승인과 도구 선택은 SKILL.md 서브에이전트 운용 절.

## 0. 난이도 판정 → 렌즈 스케일

리뷰 비용은 작업 무게에 비례해야 한다. 실측에서 wall-clock 병목은 렌즈 개수가 아니라 정적 추적 렌즈 하나였다. 그래서 ④ 의 깊이는 **effort 를 올려서가 아니라 케이스 상한으로** 조절한다 - effort 를 올리면 같은 케이스 수를 붙들고 오래 생각하는 쪽으로 새고, 리뷰에서 실제로 잡히는 것은 케이스의 다양성이다.

**렌즈 effort 기본 상한은 `high` 다** - 근거와 예외 절차는 [notebook/common/model-routing.md](../notebook/common/model-routing.md) §3. **아래 표의 effort 가 기본값이다.** 한 단계 올리거나 내릴 때는 플랜 결정 로그에 근거 한 줄을 남긴다(예: ⑤ 가 대조할 리터럴이 3개면 내리고 30개면 올린다).

| 난이도 | 신호 | 렌즈 구성 | ④ 케이스 상한 | effort 기본값 |
|---|---|---|---|---|
| 경량 | 파일 1~2, 검증된 패턴 복제, 회귀 표면 좁음 | ④⑤ 2렌즈 | 4 | 전부 medium |
| 표준 | 파일 3~6 또는 신규 모듈 하나, 통합 지점 뚜렷 | ①~⑤ 5렌즈 | 8 | ④ high, 나머지 medium |
| 중(重) | 다파일 리팩토링/이식, 데이터 이행, 아키텍처 영향, 실패 비용 큼 | ①~⑤ + 카탈로그 렌즈(작업 성격 매칭) = 7개 이상 | 12 | ①②④ high, 조사형은 medium~high, 팀 2~3 복제 검토 |

**모델은 난이도가 아니라 렌즈의 성질이 정한다.** 성질 분류는 아래와 같고, 어느 별칭이 어느 티어인지는 [notebook/common/model-routing.md](../notebook/common/model-routing.md) 가 단일 근거다(스폰 직전에 본다).

- **추론형**(없는 것을 상상해야 한다 - 상위 티어 `'opus'`): ① 구조 준수, ② 과설계, ④ 정적 추적, ⑥ 회귀·경계, ⑧ 수명·동시성
- **조사형**(답이 코드에 있고 찾아서 대조한다 - 중간 티어 `'sonnet'`): ③ 중복, ⑤ 정합성, ⑦ 데이터 이행, ⑨ 성능(실제 데이터와 호출 빈도 조사가 본체다)
- 새로 정의한 렌즈는 같은 질문으로 가른다: 그 렌즈가 무엇을 근거로 결론을 내는가 - file:line 이면 조사형, 추론이면 추론형. 조사형으로 시작해 보고가 얕으면 다음 라운드에 올린다.

- 경량에서 ④⑤ 만 남기는 근거: 실측에서 critical 을 잡은 것은 거의 전부 ④(정적 추적)와 ⑤(정합성)였다. ①②③ 은 구조가 관련된 작업에서 가치가 생긴다.
- 판정은 메인이 하고, 근거를 플랜의 "난이도" 항목에 한 줄로 기록한다. **렌즈 구성 확인은 중(重) 난이도에서만 별도 문항으로 묻는다** - 경량과 표준은 표가 정한 기본 구성으로 그냥 스폰한다(왕복을 늘릴 값어치가 없다). 묻게 되는 경우에도 새 문항을 만들지 말고 **직전 인터뷰 문항 묶음에 함께 담아** 왕복 한 번으로 끝낸다(추천 구성이 첫 옵션). 노트북 인덱스가 판정 재료에 들어간다: 대상 시스템의 lessons 밀도(함정 밀집 = 상향), facts 불변 항목 저촉(①⑥ 가중), 검증된 클론 매핑(경량 신호).
- 난이도가 판정 경계에 걸치면 한 단계 위로 올린다. 리뷰 부족으로 P4 에서 터지는 비용이 렌즈 몇 개 비용보다 크다.

## 1. 기본 렌즈 정의 (서브 프롬프트에 넣는 임무문)

- **① 구조 준수** - "이 계획이 프로젝트의 기존 구조나 진입점을 이탈하는가? 불필요하게 구조를 늘리는가(새 매니저, 우회로, 중복 시스템, 하드코딩 키)? 프로젝트 facts 의 진입점 목록과 대조하고, 이탈이라면 어느 기존 경로를 써야 하는지까지 제시하라."
- **② 과설계** - "목표 대비 과한 설계가 있는가? 요구는 100m 인데 1km 를 대비한 추상화, 옵션, 제네릭이 있는가? 과설계는 실패가 아니라 우려다. 무엇이 과한지, 걷어낸 최소안은 무엇인지, 그래도 유지할 실익이 있는지를 보고하라." - 메인은 이 우려를 기각하지 말고 `AskUserQuestion` 으로 올리되 추천안을 명시한다.
- **③ 중복** - "이 계획이 만들려는 것과 같은 일을 하는 기존 메서드, 유틸, 시스템이 이미 있는가? 같은 목적의 코드가 이미 작성 중인 곳(브랜치, 인접 파일, TODO)이 있는가? grep 으로 실증하라."
- **④ 정적 추적** - "이 초안을 evals 처럼 시험하라. 플랜의 검증 계획이 지정한 위험 케이스를 먼저 넣고, 스스로 찾은 위험 상위 케이스를 더해 **총 N개 이내**(난이도별 상한)로 구성하라 - 전 케이스 나열이 아니라 위험 순이다. 케이스마다 초안 코드를 정적으로 추적해 실제 값의 흐름을 계산하라. 실수, 놓친 분기, 기존 동작의 회귀를 찾아내라. '될 것 같다'는 답은 금지 - 케이스별 추적 결과만 인정한다."
- **⑤ 정합성** - "초안이 의존하는 모든 시그니처, 타입, 멤버, 문자열 키, 경로, id 가 실재하는지 라이브로 대조하라. 컴파일러가 잡지 못하는 것(문자열 키, 데이터 값, 리소스 경로)을 특히 주의하라 - 존재하지 않는 값에 걸린 분기는 컴파일을 통과하는 데드코드가 된다. 언어/런타임 버전이 초안의 API 사용을 지원하는지도 대조 대상이다."

## 1b. 추가 렌즈 카탈로그 (중 난이도에서 작업 성격으로 고른다)

작업 성격이 아래 위험을 건드리면 해당 렌즈를 추가한다. 카탈로그에 없는 위험이 보이면 같은 형식(허점을 찾아라 + path:line + 반환 schema)으로 렌즈를 새로 정의해도 된다.

- **⑥ 회귀·경계** (리팩토링, 일원화, 진입점 변경에) - "플랜의 회귀 경계 목록을 기존 소비자 관점에서 역추적하라. 초안 적용 후에도 기존 호출자/구독자가 같은 입력에 같은 결과를 받는가? 시그니처는 유지되어도 의미가 달라지는 지점(기본값, 호출 순서, 부수효과)을 특히 보라."
- **⑦ 데이터 이행** (스키마, 스펙 시트, 세이브 포맷 변경에) - "구버전 데이터로 부팅/로드하면 무슨 일이 나는가? 필드 추가/삭제/개명 각각에 대해 기존 저장분·기존 시트 행이 어떻게 해석되는지 추적하라. 마이그레이션 없는 암묵 기본값이 조용한 오염을 만들지 않는가?"
- **⑧ 수명·동시성** (풀링, 이벤트, async, 파괴 순서 접점에) - "구독과 해제가 짝을 이루는가? 풀 반환 후 접근, 파괴 후 콜백, 취소 없는 fire-and-forget, 재진입이 가능한 경로를 추적하라."
- **⑨ 성능** (매 프레임/대량 데이터 경로에) - "핫패스에 새 할당, 중첩 루프, 프레임당 반복 비용이 들어가는가? 호출 빈도를 file:line 근거로 추정하고 비용을 산식으로 제시하라."
- **⑩ 운영·복구** (마이그레이션 스크립트, 배치 작업, 외부 서비스 쓰기에) - "중간에 실패하면 어떤 상태로 남고, 그 상태에서 재실행하면 복구되는가 이중 적용되는가? 부분 실패가 데이터를 오염시키는 경로를 추적하라."

각 렌즈 서브의 프롬프트에 공통으로 넣을 것:
- 플랜/초안 본문 (Workflow 를 쓴다면 스크립트 리터럴로 - 아래 4절의 함정 참고)
- 프로젝트 컨텍스트: 프로젝트 루트 절대경로, facts 파일 절대경로, 컨벤션 문서 경로(있으면). 깨끗한 컨텍스트의 서브는 이것 없이는 "facts 와 대조하라"는 임무를 수행할 수 없다.
- 이번 작업과 관련된 노트북 lessons 경로 목록: "이 기록들을 먼저 읽고 대조하라 - 과거에 검증된 함정이다."
- 범위 초과 보고 규칙: 모든 렌즈에 "조사가 넘치면 '범위 초과 + 분할 제안'만 보고하라"고 지시한다. 하위 서브에이전트는 다시 위임하지 않는다 - 재분할은 메인이 한다(SKILL.md 운용 절의 오케스트레이션 기본 원칙).
- 알려진 수용 리스크 목록: "이 위치들은 사용자가 이미 수용했다 - 치명으로 다시 보고하지 마라."

## 2. 교차 검증

- 기본은 1세트다. 중(重) 난이도 중에서도 실패 비용이 특히 큰 작업(되돌리기 어려운 데이터 이행, 광범위 아키텍처 변경)이면 2~3세트 복제를 검토한다.
- 복수 세트는 같은 렌즈를 독립적으로 실행하고 메인이 결과를 교차 대조한다. 한 세트만 잡은 지적은 라이브 확인으로 판별하고, 모든 세트가 잡은 지적은 거의 확실하다.
- 1세트를 넘는 투입은 실행 전에 `AskUserQuestion` 으로 승인받는다(비용 때문이다). 렌즈 구성 확인 문항에 세트 수를 함께 실으면 왕복 한 번으로 끝난다.

## 3. 반환 schema (Workflow 용)

```js
const REVIEW_SCHEMA = { type: 'object', additionalProperties: false, required: ['findings', 'cleanWithinLens'],
  properties: {
    findings: { type: 'array', items: { type: 'object', additionalProperties: false,
      required: ['lens', 'severity', 'where', 'problem', 'fix'],
      properties: {
        lens: { type: 'string' },
        severity: { type: 'string', enum: ['critical', 'concern', 'minor'],
          description: 'critical=계획 결함(회귀 포함), concern=과설계/가치 우려(사용자 판단 대상), minor=참고' },
        where: { type: 'string', description: 'path:line - 라이브로 확인한 위치. 초안 자체면 plan:<절>' },
        problem: { type: 'string' }, fix: { type: 'string', description: '구체 수정 방향 또는 최소안' } } } },
    cleanWithinLens: { type: 'boolean' } } }
```

## 4. Workflow 골격 (병렬 렌즈 - P1 병렬 조사도 같은 모양이다)

Workflow 도구를 쓰는 이유는 `agent()` 의 effort 차등, schema 구조 반환, `parallel()` 병렬 실행이다. 이 스킬의 지시가 곧 opt-in 이다. 단일 위임이면 raw `Agent` 로 충분하다. Workflow 를 쓸 수 없는 환경이면 병렬 `Agent`(Explore) 로 같은 렌즈들을 스폰하되, 잃는 것을 보완한다: schema 강제가 없으므로 반환 규격(lens/severity/where/problem/fix 표)을 프롬프트 텍스트로 지정하고, effort 차등은 포기한다.

```js
export const meta = {
  name: 'n-worker-pre-review',
  description: 'n-worker P2 - 생산 전 적대 리뷰 (렌즈 병렬)',
  phases: [{ title: 'Review' }],
}
// 스크립트를 작성할 때 §3 의 REVIEW_SCHEMA 리터럴을 이 자리에 그대로 붙인다 - 주석만 남기면 ReferenceError 다.
phase('Review')
// 함정 1: 플랜/초안은 args 로 넘기지 않는다 - args 는 문자열화되거나 전달이 누락되어도 조용히 넘어가서,
// 서브가 undefined 를 입력으로 믿고 끝까지 실행해 버린다. 그렇다고 플랜 전문을 리터럴로 박지도 않는다 - 그 분량(실측 10~28KB)이
// 메인 출력으로 한 번 더 쌓인다. 프롬프트 문자열에는 **플랜 파일 절대경로 + 3줄 요약**만 싣고 서브가 Read 로 전문을 읽게 한다
// (경로는 args 가 아니라 프롬프트라 유실되지 않는다). 조건: 스폰 직전에 플랜 파일이 최종본이어야 한다. 아래 '입력 미전달' 가드는 그대로.
// 경로는 nb-load 가 준 슬래시 표기 그대로 - 역슬래시(C:\\...)는 JS 문자열 이스케이프로 깨진다.
const planPath = '<$WORK>/plan.md'
const planGist = `<< 3줄: 무엇을 바꾸나 / 어디까지 / 회귀 경계 >>`
const plan = `플랜 전문: ${planPath} (변경 설계 표, 코드 초안, 검증 계획의 위험 케이스는 이 파일에 있다 - 먼저 Read 하라)\n요약: ${planGist}`
const projectCtx = `프로젝트 루트: <절대경로> / facts: <절대경로> / 컨벤션 문서: <경로 또는 '없음'>`
const lessonPaths = []  // 이번 작업과 관련된 노트북 lessons 절대경로 목록 (메인이 채운다)
const risks = []        // 알려진 수용 리스크도 리터럴로
const riskNote = risks.length ? `\n수용된 리스크(치명 재보고 금지): ${JSON.stringify(risks)}` : ''
const lessonNote = lessonPaths.length ? `\n먼저 읽고 대조할 검증된 기록: ${lessonPaths.join(', ')}` : ''
const base = `다음 계획/초안을 적대적으로 리뷰하라. 통과시키지 말고 허점을 찾아라. 라이브 조사 허용, 모든 지적은 path:line.` +
  ` 계획이 비어 보이면 즉시 critical '입력 미전달' 하나만 보고하라. 조사가 넘치면 '범위 초과'와 분할 제안만 보고하라.` +
  `\n${projectCtx}${riskNote}${lessonNote}\n계획:\n${plan}`
// 렌즈 배열은 P2 의 난이도 판정 결과로 구성한다 - 경량이면 ④⑤ 2개, 표준이면 ①~⑤, 중이면 카탈로그를 더해 7개 이상.
// model 은 렌즈의 성질(추론형/조사형)로, effort 는 난이도 기본값에서 메인이 조정해 채운다 - 둘 다 §0 과
// notebook/common/model-routing.md 를 근거로 스폰 직전에 정한다. 아래는 '표준' 난이도의 한 예시다.
// xhigh 는 렌즈에 쓰지 않는다 - ④ 의 깊이는 케이스 상한 N 으로 조절한다.
const lenses = [
  { label: 'lens:구조준수',   model: 'opus',   effort: 'medium', q: '<렌즈 ① 임무문>' },
  { label: 'lens:과설계',     model: 'opus',   effort: 'medium', q: '<렌즈 ② 임무문>' },
  { label: 'lens:중복',       model: 'sonnet', effort: 'medium', q: '<렌즈 ③ 임무문>' },
  { label: 'lens:가상테스트', model: 'opus',   effort: 'high',   q: '<렌즈 ④ 임무문 - 케이스 상한 N 포함>' },
  { label: 'lens:정합성',     model: 'sonnet', effort: 'medium', q: '<렌즈 ⑤ 임무문 - 대조 대상이 많으면 메인이 high 로 올린다>' },
  // 중 난이도면 effort 를 올리고 카탈로그 렌즈를 잇는다: { label: 'lens:데이터이행', model: 'sonnet', effort: 'high', q: '<⑦ 임무문>' }, ...
]
// 함정 2: model 은 렌즈마다 명시한다 - 생략하면 세션 모델(최상위 티어)을 상속해 전 서브가 최고가로 돈다.
// 별칭은 세대 자동 추적이다(항상 그 시점의 최신 세대) - 특정 버전을 박는 것이 아니다.
const out = await parallel(lenses.map(L => () =>
  agent(`${base}\n\n네 렌즈: ${L.q}`, { label: L.label, phase: 'Review', agentType: 'Explore', model: L.model, effort: L.effort, schema: REVIEW_SCHEMA })))
// 함정 3: 죽은 서브는 null 로 온다. 그냥 filter 하면 "어느 렌즈가 죽었는지"가 사라져 재시도 규칙을 실행할 수 없다.
const dead = lenses.filter((L, i) => !out[i]).map(L => L.label)
// 함정 4: return 값은 완료 알림으로 메인 컨텍스트에 통째로 들어간다(24KB 에서 잘려 꼬리 유실 - 실측 51KB 결과에서 27KB 만 도착).
// 그래서 전문을 return 하지 않는다. 건수와 판정만 돌려주고, 전문은 하네스가 남기는 journal.jsonl 을
// `bash <스킬>/scripts/wf-summarize.sh <journal>` 로 압축해 읽는다(critical 은 전문, 나머지 축약. journal 경로는 완료 알림의 diagnostics 에 온다).
return { dead, lenses: out.map((r, i) => ({ lens: lenses[i].label, findings: r ? r.findings.length : null, clean: r ? r.cleanWithinLens : null })) }
// dead 가 비어 있지 않으면 메인이 그 렌즈만 1회 재시도한다. 취합, 분기, 사용자 질문은 전부 메인의 일이다.
```

기타 런타임 함정: `meta` 는 순수 리터럴만 허용된다. `Date.now()`, `Math.random()`, 인자 없는 `new Date()` 는 호출하면 throw 한다. 스크립트 자신은 파일과 git 에 접근할 수 없다(그것은 `agent()` 가 한다). `parallel()` 은 전부 끝나야 반환되는 배리어이고, throw 한 항목은 null 로 떨어진다. 동시 실행 상한은 자동이므로 직접 상한을 두지 않는다. 같은 스크립트가 두 번 실패(파싱/런타임)하면 골격을 접고 raw `Agent` 로 같은 일을 직접 시킨다 - 디버그 무한루프를 막기 위해서다. 골격은 수단이지 목적이 아니다.

P1 의 병렬 조사는 같은 골격에서 렌즈 대신 체크리스트 항목을 나눠 맡기는 형태다. **묶음 크기는 서브당 파일 3~6개, 상한 6** - 서브 하나에 스킬,컨벤션 문서를 읽는 고정비(실측 sonnet 5~6만 토큰)가 파일 크기와 무관하게 붙으므로 9줄짜리 파일에 서브 하나를 주지 않는다(실측 23개 서브 93만 토큰). 깊이는 schema 로 지킨다 - 파일별 항목 배열을 두고 파일 수와 항목 수가 다르면 그 서브만 재실행. probe 는 답이 코드에 있는 조사형이므로 `{ label: 'probe:<항목>', agentType: 'Explore', model: 'sonnet', effort: 'low' }` 을 기본값으로 하고(사전 조사는 좁게, 병렬로 - SKILL.md 오케스트레이션 기본 원칙), 항목마다 메인이 조정한다 - 구조를 따라가야 하면 medium, 설계 의도까지 읽어야 하는 항목이면 추론형으로 보고 `model: 'opus'` + effort high 로 올린다. 반환 schema 는 `{ item, verdict: 'ok|broken|notfound', evidence(path:line), note }` 로 한다.

## 5. 취합 후 분기 (메인)

```
critical → 해당 지점만 P1 재진입 → 재수렴 → 재리뷰 (같은 게이트 2회째 재실행이면 AskUserQuestion 진행/포기, 횟수는 플랜 결정 로그에 기록)
concern  → 우려와 대안을 대화에 렌더 → 플랜 리스크 절 갱신 → 같은 턴에서 이어서 AskUserQuestion (추천 명시) → 수용되면 "알려진 수용 리스크"에 올린다
minor/이상 없음 → 대화에 플랜 렌더 → 플랜 최종본 파일 반영 → 같은 턴에서 이어서 AskUserQuestion 승인 → P3
```

렌더와 파일 갱신 뒤에는 **턴을 끝내지 말고 그 턴에서 바로** 질문한다(SKILL.md 준칙). 출력만 하고 멈추면 사용자에게는 아무것도 안 물어본 정지로 보인다. 오타 방지는 질문 본문을 결정문만으로 짧게 유지해서 한다.

렌즈 하나의 "이상 없음" 판정은 `findings 0건 && cleanWithinLens === true` 다. findings 0건인데 cleanWithinLens 가 false 면 렌즈가 판정을 끝내지 못한 것이므로(범위 초과 등) 결과를 신뢰하지 말고 분할 재실행한다.

"더 나은 방식이 있는가"는 취합하는 메인이 스스로 묻는다. 렌즈 결과를 종합하면 대안이 보이는 경우가 많다. 있으면 concern 과 같은 경로로 사용자에게 올린다.
