# 검증 - 실행 결과와 확인 범위

## 1. 수단 선택

적용되는 단계 카드, 프로젝트 facts/infra, 프로젝트의 빌드/테스트/린트 설정 순서로 수단을 찾는다. 기본은 변경된 소스가 포함된 컴파일과 관련 테스트다. 기존 검사가 부족하면 이번 위험을 재현하는 작은 테스트나 검증 스크립트를 추가한다.

- 검사 대상 소스/어셈블리와 실행 결과의 신선도를 확인한다. 오래된 DLL이나 실행되지 않은 테스트는 현재 변경의 근거가 아니다.
- 문자열 키, 리소스 경로, 직렬화 참조, 데이터 값은 실제 대상/소비처와 연결되는지 확인한다. 가능한 반복 검사는 스크립트로 묶는다.
- 에셋/외부 쓰기는 반환 메시지뿐 아니라 저장된 결과를 읽어 확인한다. 타임아웃이어도 작업이 적용됐을 수 있어 재실행 전에 상태를 확인한다.
- 실제 diff 리뷰가 필요하면 [review.md](review.md)의 위험 기준으로 범위를 정한다.

## 2. 실행과 로그

출력이 큰 명령은 `> "$WORK/<이름>.log" 2>&1`로 저장하고 종료 상태와 실패 부분만 읽는다. 성공 시에는 검사 범위와 판정 근거 한두 줄이면 충분하다. 로그가 짧으면 메인이 직접 보고, 원인 판독이 크고 독립적일 때만 위임한다.

비동기 도구는 공식 완료 알림이나 상태 조회 수단을 사용한다. 같은 고착/실패 신호가 반복되면 알려진 복구 수단이나 사용자 핸드오프로 전환한다. 새 에이전트로 같은 진단을 반복하기보다 확인 범위와 실행 환경의 제한을 남긴다.

## 3. 사용자 핸드오프

Claude가 직접 수행할 수 없는 확인만 요청한다.

- **현재 상태:** 무엇이 완료됐고 무엇을 확인해야 하는지 한 줄.
- **번호 단계:** 한 단계에 동작 하나. 대상 화면/테스트와 정상 결과를 지정한다.
- **검증:** 어떤 결과를 회신하면 되는지.

자동 검사로 이미 확인한 표면은 중복 요청하지 않는다. 같은 관측을 반복해도 원인이 좁혀지지 않으면 요청 범위나 관측 수단을 바꾼다.

## 4. 수정과 완료

- 실패 증상(에러 문자열, 증상 키워드)은 원인 추리 전에 nb-grep으로 대조한다 - 기록된 함정이면 그 본문이 가장 싼 진단이다. 같은 증상의 조사와 검색 결과는 재사용한다.
- 수정 뒤에는 실패했던 검사와 영향받는 회귀 검사를 다시 실행한다. 공유 계약을 바꿨으면 그 소비자 검사까지 넓힌다.
- 설계/범위/사용자 의도가 바뀌어야 하면 해당 결정만 다시 확인한다.
- 완료 보고에는 실행한 검사, 확인한 표면, 미검증 표면을 구분한다. 중요한 실패가 남아 있으면 차단 상태다. 사용자만 확인할 수 있는 동작은 사용자 확인 후에 닫는다.
