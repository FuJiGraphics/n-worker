# 검증 - 자동 검증, 로그 판독, 핸드오프

> P4 의 상세다. 검증 반복의 주체는 메인이며, 요청한 변경이 의도대로 동작할 때까지 멈추지 않는다.

## 1. 자동 검증 수단의 결정

우선순위는 다음과 같다:
1. **채택된 단계 카드** - 카드가 절차와 수단을 명시한다. 카드의 절차가 우선한다.
2. **프로젝트 facts / infra 항목** - 노트북에 검증 수단이 기록되어 있으면 그것을 쓴다.
3. **라이브 발견** - 둘 다 없으면 프로젝트에서 직접 찾는다: 빌드/테스트/린트 명령(`package.json` 의 scripts, `Makefile`, `*.sln`, gradle, cargo, CI 설정). 여기서 찾은 수단은 P5 의 기록 후보다 - 다음 작업의 조사 비용을 줄여주므로 기록 게이트를 통과한다.

돌릴 수 있는 것은 Claude 가 직접 돌린다. 사용자에게 넘기는 것은 "Claude 가 할 수 없는 것"뿐이다.

## 2. 로그 판독 (메인 컨텍스트 보호)

- **원문 전체를 메인 컨텍스트에 들이지 않는다 - 직접 돌릴 때도.** 출력이 수십 줄을 넘을 수 있는 명령은 `> "$WORK/<이름>.log" 2>&1` 로 리다이렉트하고, 실패/에러 부분만 grep·tail 로 발췌해 읽는다. 통과했으면 판정 근거 한두 줄이면 족하다. 원문은 파일로 남아 있으므로 필요할 때 다시 발췌하면 된다.
- 출력이 가볍고(수십 줄) 판독이 단순하면 메인이 직접 돌리고 읽는다. 서브 왕복이 오히려 비싸다.
- 로그가 수백 줄이고 판독까지 무거우면(여러 면의 회귀 확인, 교차 대조) 서브에 "돌리고 에러와 실패만 요점 보고하라"고 위임한다(답이 로그 안에 있는 조사형이므로 `model: 'sonnet'`, 여러 시스템에 걸친 원인 추론까지 필요하면 `'opus'`). 서브는 상태를 유지하지 않고, 반환은 실패 항목과 증거(로그 발췌 1~3줄)만 받는다.

## 3. 핸드오프 출력 형식 (사용자가 해야 진도가 나가는 단계)

줄글 설명이 아니라 체크리스트형 작업 지시서로만 전달한다:

- **[현재 상태]** 한 줄 - 무엇이 있고 무엇이 없는지.
- **번호 단계** - 한 단계는 동작 하나이고 동사로 시작한다. 여러 동작을 한 단계에 뭉치지 않는다.
- 모르는 값(경로, 수치)은 `확인 필요` 로 표시한다. 추측해서 채우지 않는다.
- 마지막에 **[검증]** 한 줄 - 제대로 됐는지 어떻게 확인하는지.
- 금지: 줄글 문단, 배경 설명, "~하면 됩니다" 식의 장황한 문체.

요청할 표면은 정확히 지정한다. "전부 확인해달라"가 아니라 가장 위험한 표면부터, 무엇이 보여야 정상인지 명시한다. 결과 회신을 받으면 다음으로 넘어간다.

## 4. 반복 규칙

- 실패 증상을 보면 원인 분석 전에 3레이어 lessons-index 를 증상 키워드로 대조한다(SKILL.md 준칙의 노트북 대조 규율). 같은 함정이 이미 기록되어 있으면 그 본문이 가장 싼 진단이다. 없으면 그때 원인 분석에 들어간다.
- 문제가 보고되면 원인을 분석하고, **기존 구조를 벗어나지 않게** 수정한 뒤 다시 검증한다. 수정하다가 구조를 벗어나고 싶어진다면 그것은 설계 문제이므로 P1/P2 로 되돌린다.
- 회귀 경계(플랜의 "유지해야 할 기존 동작")는 매 반복에서 함께 확인한다.
- 완료 판정: 사용자만 확인할 수 있는 표면이 있으면 사용자의 확인이 기준이고, 전 표면이 자동 검증으로 덮이면 그 결과가 기준이다. 어느 쪽이든 Claude 의 "될 것이다"는 근거가 아니다.
