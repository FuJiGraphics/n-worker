# 인터뷰 - 착수에 필요한 결정만 확인

## 0. 목적

모든 가능한 선택을 확정하는 단계가 아니다. 사용자에게 결과가 달라지는 미정만 확인하고 구현에 필요한 근거를 모은다. 산출물은 [plan.md](plan.md)의 짧은 플랜이다. 프로젝트 파일은 P2 착수 판단 전까지 읽기 전용이다.

## 1. 질문 기준

- 의도, 정책, 공개 계약, 데이터 손실 가능성, 큰 범위 변경을 결정해야 하면 묻는다.
- 코드로 답할 수 있는 위치, 시그니처, 기존 동작은 직접 확인한다.
- 되돌리기 쉬운 구현 상세는 기존 패턴을 따르고 플랜에 한 줄로 명시한다. 가능성이 있다는 이유만으로 옵션을 열지 않는다.
- 요청에 답이 이미 있으면 다시 묻지 않는다. 플랜 표시 방식, 카드 채택, 보고서 여부는 기본 질문에서 제외한다.
- 독립된 질문은 `AskUserQuestion` 한 번에 묶는다(최대 4문항). 부모 답에 따라 달라지는 자식 질문은 실제로 필요할 때만 후속으로 묻는다.
- 추천을 첫 옵션에 두고 결정의 근거는 짧게 설명한다. 질문이 없으면 계속 진행한다.
- **기존 용어와 충돌하면 즉시 지적한다.** 프로젝트 노트북 facts에 이미 정의된 용어와 사용자의 말이 다르면 그 자리에서 되묻는다. "facts는 이 용어를 X로 정의하는데 Y를 뜻하시는 것 같습니다. 어느 쪽입니까?"

## 2. 조사와 근거 재사용

1. 가까운 기존 구현과 관련 지침을 찾는다. 조사 대상 목록(파일, 시스템, 외부 서비스, 증상)이 모이면 스폰이나 직접 조사 전에 nb-grep으로 3레이어 인덱스와 대조한다(SKILL.md 노트북 대조 규율). 이미 기록된 항목은 본문 열람으로 조사를 대체한다. 단 동작을 걸 값은 라이브 재확인 원칙이 그대로 적용된다.
2. 조사 항목은 “무엇이 확인되면 결정을 내릴 수 있는가”로 좁힌다. 짧은 Read/grep 몇 개는 메인이 묶어 실행한다.
3. 독립된 큰 조사가 여러 개일 때만 병렬 위임한다. 항목 2개, 파일 3개 같은 숫자로 스폰하지 않는다. 고정 컨텍스트를 읽는 비용보다 충분히 큰 일인지 판단한다.
4. 서브 입력은 대상 범위와 질문, 근거 위치, 관련 lesson 경로, `$WORK`와 nb-grep 호출법이다. 반환은 항목별 결론, 근거, 미확인 범위만 받는다. 모델과 도구 선택은 [review.md](review.md) §4와 model-routing을 따른다.
5. 확인된 근거는 참조 파일이 바뀌거나 새 증거와 모순되지 않으면 재사용한다. 추가 질문에 답하려고 기존 조사를 전부 새로 스폰하지 않는다.

## 3. 착수 조건

- 목표와 수정 범위가 명확하다.
- 사용자 판단이 필요한 미정이 남지 않았다.
- 구현 방향과 적절한 레퍼런스가 있다. 새 영역이라 레퍼런스가 없으면 그 사실과 선택한 최소 설계를 적으면 된다.
- 검증 수단과 중요한 회귀 경계를 정했다.
- 확정된 항목마다 근거가 적혀 있다(사용자 답 / file:line / 노트북 항목).

`notfound`는 부재의 증거도 통과도 아니다. 구현에 필수인 의존성을 못 찾았으면 조사 범위를 좁히거나 사용자에게 전제 충돌을 알린다. 선택적 자료는 못 찾았다는 제한을 남기고 진행한다. 미정 0을 만들려고 무관한 조사를 반복하지 않는다.

결정이 바뀌면 영향을 받는 플랜 절만 수정한다. 이미 확정된 다른 결정까지 무효화하지 않는다. 핵심 코드 초안, 모든 결정의 상세 로그, 라운드별 HTML 재생성은 요구하지 않는다.
