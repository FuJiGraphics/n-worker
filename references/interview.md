# 인터뷰 - 결정 트리 순회

> **플랜을 결정의 트리로 보고 모든 가지를 방문한다.** 목적은 빨리 합의하는 것이 아니라, 암묵적으로 가정된 결정을 하나도 남기지 않는 것이다. 순회가 끝난 플랜은 모든 가지가 방문된 플랜이다.
> **코드가 답할 수 있는 질문은 사용자에게 묻지 않는다.** 코드를 읽어서 답한다. 사용자에게 묻는 것은 코드에 답이 없는 것, 즉 의도와 정책과 취향뿐이다.

## 0. 산출물 - 플랜

인터뷰의 산출물은 답변 모음이 아니라 **플랜**이다. `$WORK/plan.md` 에 [plan.md](plan.md) 포맷으로 유지하고, 사용자가 언제 열어봐도 "확정된 것 / 미정인 것 / 현재 설계"를 볼 수 있어야 한다. 답이 올 때마다 갱신하되 바뀐 절만 고친다([plan.md](plan.md) §1). 컨텍스트가 아니라 파일이 스펙의 원본이다.

이 단계 동안 프로젝트 파일은 읽기 전용이다(SKILL.md P1 의 편집 잠금).

## 1. 순회 규칙

- **트리를 연다.** 요청을 받으면 먼저 그 안에 숨은 결정들을 트리로 늘어놓는다. 부모 결정을 확정한 뒤에 거기 딸린 자식 결정으로 내려간다. 아직 확정하지 않은 가지는 전부 플랜 미정 절에 올린다 - 미정 절이 곧 남은 가지 목록이다.
- **의존 관계가 있는 결정은 같은 호출에 묶지 않는다.** 부모의 답에 따라 자식의 선택지 자체가 바뀌므로, 부모를 먼저 묻고 답을 받은 뒤 자식을 만든다. 서로 독립인 결정만 한 호출에 묶는다(`AskUserQuestion` 4문항 상한).
- **질문은 `AskUserQuestion` 으로 내고 첫 옵션이 추천안이다**(SKILL.md 준칙 - 추천은 전 문항 필수). 사용자는 빈 프롬프트를 보는 것이 아니라 제안에 반응해야 한다.
- **레퍼런스는 이른 가지로 확정한다.** 본뜰 기존 구현을 먼저 고르게 하고(후보가 여럿이면 file:line 으로 제시), 레퍼런스와 같은 부분은 묻지 않는다 - 다른 부분만 가지로 남는다.
- **회귀 경계는 반드시 방문하는 가지다.** 유지해야 할 기존 동작을 확정 절에 명시한다 - 플랜 검증 계획의 회귀 경계 칸과 렌즈 ⑥ 의 입력이다. 순회 중 코드 외 접점(에셋, 설정, 배선)이 새로 드러나면 해당 단계 카드의 채택을 다시 확인한다.
- **부모가 뒤집히면 그 아래 가지를 전부 무효화하고 다시 순회한다.** 뒤집힌 전제 위에 쌓인 결정을 들고 가지 않는다.
- **답이 올 때마다 플랜을 갱신한다.** 모아서 나중에 반영하지 않는다.
- 이미 명확한 것은 묻지 않는다. 라운드 수에는 제한이 없지만, 정보를 더하지 않는 질문은 0개여야 한다.

## 2. 순회 중 쓰는 기법

**모호한 용어는 정확한 용어로 바꾼다.** 여러 뜻으로 쓰이는 단어가 나오면 정식 용어를 제안한다. "계정이라고 하셨는데 사용자 계정입니까, 결제 주체입니까 - 이 둘은 다른 것입니다." 대상은 코드에 실재하는 이름(타입명, 메서드명, 에셋명, 문자열 키)으로 확정하고, 통칭 하나가 실재 심볼 여럿에 걸리면 어느 것인지 고르게 한다.

**기존 용어와 충돌하면 즉시 지적한다.** 프로젝트 노트북 facts 에 이미 정의된 용어와 사용자의 말이 다르면 그 자리에서 되묻는다. "facts 는 이 용어를 X 로 정의하는데 Y 를 뜻하시는 것 같습니다. 어느 쪽입니까?"

**구체 시나리오로 경계를 확정한다.** 개념 사이의 관계가 나오면 경계가 되는 시나리오를 만들어 묻는다. "A가 진행 중일 때 B가 들어오면 어떻게 됩니까?" 추상적으로만 합의된 관계는 P3 에서 각자 다르게 구현된다.

**진술을 코드와 대조해 모순을 드러낸다.** 사용자가 "이건 이렇게 동작한다"고 진술하면 코드가 동의하는지 확인한다. 어긋나면 넘기지 말고 즉시 올린다. "코드는 X 전체를 처리하는데 부분 처리가 가능하다고 하셨습니다. 어느 쪽입니까?" 진술과 코드가 어긋난 채로 플랜에 들어가면 P3 에서 갈라진다.

**용어는 확정되는 즉시 플랜에 적는다.** 배치 금지. 확정된 용어 중 사용자만 알 수 있는 것은 P5 에서 curator 에게 facts 기록 제안으로 넘긴다.

**결정 로그에는 기준을 통과한 것만 올린다.** 되돌리기 어렵고, 맥락 없이 보면 놀랍고, 실제 트레이드오프의 결과일 때만 결정 로그에 올린다([plan.md](plan.md) §1의 3조건). 나머지는 확정 절 한 줄로 끝낸다.

## 3. 병렬 조사 - 코드가 답하는 질문의 처리

코드를 읽어야 답이 나오는 항목이 여럿 쌓이면 서브에 나눠 맡긴다. 메인이 먼저 **검증할 목록**을 만든다. 항목마다 "무엇을 / 어디서(추정) / 무엇이 확인되면 통과"가 명확해야 한다. 명확하게 쓸 수 없는 항목은 아직 트리가 덜 전개된 것이므로, 더 쪼개거나 사용자에게 먼저 묻는다.

스폰 전에 목록을 3레이어 lessons-index 와 대조한다(SKILL.md 준칙의 노트북 대조 규율). 이미 기록된 항목은 본문 열람으로 조사를 대체한다. 단 동작을 걸 값은 라이브 재확인 원칙이 그대로 적용된다.

- **항목이 2개 이상이면 `Workflow` 로 스폰한다**(골격은 [review.md](review.md) §4 끝의 P1 조사 변형 - 체크리스트 공유분을 스크립트에 1회만 쓰고 항목별 effort 를 가른다). 1개일 때만 `Agent`. 읽기 전용이므로 `agentType: 'Explore'`. 모델과 effort 는 SKILL.md 서브에이전트 운용 절. **서브 하나에 파일 3~6개(상한 6)** 를 묶어 준다 - 파일당 서브 1개는 고정비만 늘린다(review.md §4 끝). 결과는 return 이 아니라 journal 을 `scripts/wf-summarize.py` 로 읽는다.
- 서브 프롬프트에 넣을 것: 검증 항목(체크리스트), file:line 인용 강제, "추측 금지 - 못 찾으면 못 찾았다고 보고하라", 반환은 항목당 1~3줄 요점만, 범위 초과 보고 규칙("조사가 넘치면 범위 초과와 분할 제안만 보고하라").
- 결과 처리: 통과한 항목은 플랜의 근거가 되고, 깨진 항목은 다음 질문이나 설계 수정으로 이어진다. 재확인 범위는 SKILL.md 준칙의 신뢰 규율을 따른다.

라운드마다 새 서브로 실행한다. 이전 맥락이 남지 않은 컨텍스트로 보는 것이 목적이다.

## 4. 수렴 판정

아래가 모두 성립하면 수렴이다.

- 플랜 미정 절이 비었다(= 트리에 남은 가지가 없다).
- 확정 절 전 항목에 근거가 적혀 있다(사용자 답 / file:line / 노트북 항목).
- 레퍼런스가 file:line 으로 확정되어 있다(P3 의 복제 대상).
- 마지막 병렬 조사에서 `broken` 0 **그리고 `notfound` 0**. `notfound` 는 "못 찾았다"이지 "없다"가 아니므로 그대로 두면 추측과 같다 - 재조사하거나 전제 충돌로 사용자에게 올린다.

수렴하면 플랜에 "파일별 변경 계획 + 핵심 코드 초안"(P2 의 입력)을 채우고 P2 로 넘어간다.

수렴이 안 되는데 물을 것도 없다면 조사가 부족한 것이다 - 병렬 조사를 먼저 돌린다.
