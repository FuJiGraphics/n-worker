# html 렌더와 결과 보고서 규격 (plan.html, report.html)

> 읽는 주체가 제한된 파일이다: **§1~2 는 html 추적 모드(②)를 고른 세션의 메인과 reporter 서브**, **§3 은 reporter 서브만** 읽는다. md 추적 세션의 메인은 이 파일을 로드하지 않는다 - 플랜 뼈대는 [plan.md](plan.md) §1 이 기준이다.

## 1. html 생성 공통 절차 (plan.html 과 report.html 모두)

1. [../assets/page-template.html](../assets/page-template.html) 을 읽어 `{{TITLE}}` 과 `{{BODY}}` 를 치환한 뒤 목적 경로로 쓴다.
2. **완전 자립형 단일 파일 원칙.** 외부 요청 0건이다: CDN 스크립트, 외부 CSS/폰트, 다른 로컬 파일 참조, JS 전부 금지. 근거: CDN mermaid 를 쓰던 시절, 차단/오프라인 환경에서 다이어그램이 원문 텍스트로 깨지는 사고가 반복됐다. 다이어그램은 손으로 그린 inline SVG, 이미지는 base64 data URI 내장, 코드 색은 수동 span(§2)으로 해결한다.
3. 상태별 색 클래스: 확정 `.ok`, 미정 `.pending`, 우려/수용 리스크 `.warn`, 채택안과 채택 이유 `.pick`, 그림 설명 `.caption`.
4. 첫 생성 때만 `../scripts/open-artifact.sh` 로 연다(SKILL.md 준칙 - `open` 직접 호출 금지). 이후에는 같은 경로에 덮어쓰고 사용자는 새로고침으로 최신을 본다. md 가 원본이고 html 은 뷰이므로 md 도 항상 함께 갱신한다. html 재생성은 라운드마다가 아니라 **사용자 확인 직전에만** 한다 - 질문과 질문 사이의 중간 상태는 사용자가 볼 일이 없다.

## 2. {{BODY}} 작성 규칙 - 렌더링이 깨지는 지점들

과거 보고서에서 다이어그램 파손, 굵은 글씨 미표시, 코드블럭 내용 증발이 반복되었다. 원인은 전부 아래 규칙 위반이었으므로 하나도 생략하지 않는다.

**마크다운 잔재 금지.** html 본문에 `**굵게**`, 백틱, 백틱 3개 코드 펜스가 남으면 브라우저는 그 문자를 그대로 보여준다. 반드시 `<strong>`, `<code>`, `<pre><code>` 로 변환한다.

**코드블럭 안의 `<` `>` `&` 는 반드시 이스케이프한다.** `List<int>` 나 `a -> b` 를 그대로 넣으면 브라우저가 태그로 해석해 그 뒤 내용이 통째로 사라진다. `&lt;` `&gt;` `&amp;` 로 쓴다. 제네릭, 화살표, 비교 연산자가 든 코드는 특히 위험하다.

**코드 블럭은 수동 하이라이팅.** 템플릿의 pre 배경은 라이트/다크 무관 어두운 색(#1e1e2e) 고정이라 색이 항상 성립한다. 6클래스만 쓴다: 키워드 `.k`(보라), 타입 `.t`(하늘), 메서드 `.m`(파랑), 숫자 `.n`(주황), 주석 `.c`(회녹), 상수/필드 `.f`(노랑). 규칙 세 가지: 전문이 아니라 그 결정이 드러나는 핵심부만 발췌한다. 파일명을 첫 주석으로 단다. 코드 안 주석은 "무엇"이 아니라 "왜"를 적는다(예: "첫 프레임 글리치 방지 - 렌더 전에 시작점 고정").

**다이어그램은 손으로 그린 inline SVG.** 레시피:
- `viewBox` 로 좌표계를 고정하고 너비는 CSS 가 반응형으로 줄인다.
- 노드는 `rect`(rx 8) + 제목/부제 `text` 2줄. 텍스트와 화살표는 `fill="currentColor"` / `stroke="currentColor"` 로 라이트/다크 겸용, 박스 배경과 테두리는 `#8881`/`#8888` 류 반투명색.
- 이번 작업의 **신규 요소는 초록(#67c23a) 스트로크**로 기존 요소와 구분한다.
- 화살촉은 `defs` 의 `marker` 하나를 정의해 재사용한다.
- 레이어 스택, 타임라인, 비율 막대 같은 단순 구조는 SVG 보다 HTML div 바가 낫다(작성 실수 여지가 적다). 템플릿의 `.bar`(트랙) / `.bar-fill`(채움, width 를 %로) 클래스를 쓴다.

**ASCII 아트 다이어그램은 쓰지 않는다.** 한글은 고정폭 폰트에서 폭이 라틴 문자의 정수배로 정렬되지 않아, 한글이 섞인 박스/화살표 정렬은 보는 환경에 따라 반드시 깨진다.

**시각 산출물은 말로만 보고하지 않는다.** 텍스처, UI, 연출처럼 결과가 눈에 보이는 작업이면 실제 산출물을 실제 색으로 합성한 전/후 비교 이미지를 data URI 로 내장한다. 필요하면 실사용 배율로 축소한 근사 이미지도 함께 만든다. 합성에 쓴 스크립트는 P5 스크립트 등록 후보다.

**문체.** 단락은 1~2문장으로 짧게 끊는다. 논문투 라벨("본 문서에서는")을 금지한다. 수치 주장에는 산식을 병기한다(예: "수요 3.6배 = 장수 2배 x 수명 1.8배").

**자가 점검 (html 을 쓴 직후 실행한다):**
```bash
grep -nE "\*\*|\x60\x60\x60" <파일>.html      # 마크다운 잔재 - 결과 0
grep -n "{{" <파일>.html                       # placeholder 치환 누락 - 결과 0
grep -nE "<script|src=\"http|href=\"http" <파일>.html   # 자립형 위반 - 결과 0
```
코드블럭에 제네릭이나 화살표를 넣었다면 이스케이프가 됐는지 해당 구간을 눈으로 한 번 더 확인한다.

## 3. 결과 보고서 (P5 에서 사용자가 예라고 했을 때만)

> 이 절과 §1~2 는 [../agents/reporter.md](../agents/reporter.md) 가 읽는 작업 지침이다. 메인은 reporter 를 스폰하고(SKILL.md P5) 반환된 경로를 여는 것까지만 한다.

### pdf 변환 (기본 선택지)

저장 디렉터리, 파일명, 변환 도구 경로는 작업 명세로 받는다 - 관례의 원본은 노트북이고, 이 파일에는 사용자/프로젝트/환경 종속 사실을 적지 않는다. pdf 를 선택받으면:

1. `$WORK/report.html` 을 아래 구조 규칙대로 생성하고 §2 자가 점검을 돌린다.
2. Chrome 계열 headless 로 변환한다. 실행 파일은 명세의 경로를 쓰고, 없으면 환경에서 찾는다(macOS 앱 경로, PATH 의 `google-chrome`/`chromium` 순):
```bash
"<chrome 실행 파일>" --headless --disable-gpu \
  --no-pdf-header-footer --print-to-pdf="<저장 디렉터리>/<파일명>.pdf" "file://$WORK/report.html"
```
3. 변환 명령을 실행하기 **전에** 같은 경로가 이미 있는지 확인하고(`--print-to-pdf` 는 무조건 덮어쓴다), 있으면 파일명에 날짜를 붙여 비켜간다.
4. 생성된 pdf 경로와 html 원본 경로를 반환한다. 여는 것과 사용자 안내는 메인이 한다(`scripts/open-artifact.sh`).
5. 변환 도구가 없으면 html 로 폴백하고 그 사실을 반환에 적는다.

템플릿에 인쇄 CSS(`@media print` - 색 보존, 절단 방지)가 들어 있으므로 변환에 별도 조치는 필요 없다.

### report.html 작성 기준

보고서는 변경 파일 나열이 아니라 **기술 문서**다. 이 세션에 없던 동료가 읽고 "왜 이 작업이 필요했고, 어떤 구조로 풀었고, 왜 다른 방식이 아니라 이 방식이며, 무엇으로 확인했는지"를 재구성할 수 있어야 한다. 빈약한 보고서의 주원인은 재료 부족이 아니라 요약하면서 버리는 것이다 - 플랜의 결정 로그, 리뷰가 잡아낸 지적, 배제한 대안이 전부 원재료이므로 버리지 말고 옮긴다.

분량은 작업 무게에 비례한다. 설계 결정이 여러 개였던 작업이면 읽는 데 5~10분이 정상이고, 변경 0으로 끝난 작업(전제 충돌 등)이면 근거 표 중심으로 짧게 쓴다. "간결하게"를 이유로 결정 근거나 코드를 빼지 않는다.

### 문장 규칙 (AI 문체 제거 - §2 문체 규칙에 더해 적용한다)

- **의미 부풀리기 금지.** "중요한 전환점이 되었다", "더 넓은 흐름을 반영한다" 같은 의의 서술을 걷어내고 사실만 남긴다.
- **문장 꼬리 늘이기 금지.** "~함으로써", "~을 통해", "~하며" 로 문장 끝에 깊이를 흉내내지 않는다. 인과가 실제로 있으면 별도 문장으로 쓴다.
- **평가어 대신 측정 서술.** "강력한", "매끄러운", "혁신적인" 대신 수치나 동작으로 쓴다.
- **3항 나열 강박 금지.** 항목이 2개면 2개로 끝낸다. 숫자를 채우려 항목을 만들지 않는다.
- **거짓 범위 금지.** "A부터 B까지"는 실제 축이 있을 때만 쓴다.
- **권위 클리셰 금지.** "본질적으로", "핵심은", "진짜 문제는" 을 앞세우지 않는다 - 뒤에 올 문장을 그냥 쓴다.
- **예고 문구 금지.** "살펴보자", "정리하면" 없이 바로 내용을 쓴다.
- **조각 헤더 금지.** 제목 아래에 제목을 되풀이하는 한 줄 워밍업을 넣지 않는다.
- **격언 공식 금지.** "X 는 Y 의 Z 다" 식 잠언 대신 구체 주장을 쓴다.
- **마무리는 마지막 구체 사실로 끝낸다.** "앞으로가 기대된다" 류 상투 결말 금지.
- **특수문자 `·` 와 `—` 를 쓰지 않는다.** 구분자는 `-`, 나열은 `,`.

### 구조 (이 순서 고정. 해당 없는 절만 뺀다)

1. **요약** - 증상/요청, 원인, 해법을 3문장 이내의 완결된 문단으로.
2. **문제 진단** - "배제한 가설" 표(| 가설 | 검증 근거 file:line | 판정 |)를 먼저, 그 다음 확정 원인. 원인이 공간/구조적이면 여기에도 그림을 쓴다. 증상 기반이 아닌 신규 기능 작업이면 이 절 대신 **배경과 목적**(왜 이 작업이 생겼고 무엇이 좋아지는가)을 쓴다.
3. **전체 흐름** - 최종 구조의 SVG 플로우차트 1개. 수명이나 시간 축이 있으면 타임라인(div 바)을 병행한다.
4. **구현 방식과 선택지** - 이 보고서의 심장이며 가장 길어야 정상인 절. 기술 **결정마다 소절 하나씩** 나누고, 각 소절은:
   - 선택지 표 (| 선택지 | 장단점 또는 판정 |). **채택안만 bold** 처리하고, 기각된 대안도 기각 사유와 함께 반드시 남긴다(재론 방지).
   - 채택 이유는 `.pick` 초록 콜아웃, 수용한 리스크는 `.warn` 노랑 콜아웃으로 본문과 시각 분리.
   - 그 결정을 구현하는 핵심 코드 발췌(§2 코드 규칙).
   - 수치/공식은 산식과 파생 근거를 병기.
5. **검증 방법론** - 무엇으로 검증했고 각 단계가 잡은 결함을 표로(| 렌즈/수단 | 잡아낸 것 | 처리 |). 확인한 표면을 명시하고("검증됨"으로 뭉뚱그리지 않는다), 미검증 표면과 수용 리스크는 `.warn` 으로 남긴다.
6. **튜닝 노브 표** - 사용자가 이후 조정할 상수 (| 상수 | 위치 | 현재값 | 의미 |). 피드백 라운드 반영분은 R번호를 병기한다.
7. **남은 일 / 커밋 주의** - 사용자가 해야 할 일, 커밋 시 주의. 이번 세션 산출물이 아닌 변경(에디터 직접 작업분 등)을 구분해 준다.
8. **기록** - 노트북 기록과 등록 스크립트. 없으면 "없음"과 그 이유 한 줄.

생성한 뒤 §2 자가 점검을 돌린다. html 만 남기는 경우에도 경로 반환까지가 reporter 의 일이며, 여는 것은 메인이다.
